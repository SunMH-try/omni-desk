## 0. 执行摘要


本方案不是将原有“面向私有数据资产的智能知识与内容创作 Agent”简单迁移到飞书，而是在其 Agentic RAG、PageIndex 树索引、模块化服务、SSE 流式响应、MCP 工具封装和可观测性思路之上，重新面向“企业办公知识整合与分发”赛题构建一个更强调主动服务、场景触发和协作闭环的参赛作品。

作品名称建议为 **Team Knowledge Pulse Agent**，中文名可称为“团队知识脉冲助手”或“知脉 Agent”。它的核心不是“用户问一句，系统答一句”，而是持续监听团队的协作上下文：本周哪些文档被频繁修改、哪些会议形成了关键决议、哪些任务反复延期、哪些群聊讨论出现争议、哪些知识被新成员反复询问。系统将这些原始信息加工为结构化的“知识原子”（Knowledge Atom），进一步构造成“证据图谱”（Evidence Graph），再根据用户角色和场景生成不同形态的知识产物：会前背景卡片、会后行动项卡片、每周工作总结与风险洞察、团队重点事项推进表、CLI 终端提醒、飞书群推送卡片、飞书文档沉淀页和多维表格记录。

本方案选择赛题探索方向 A、B、D 进行组合，但主线保持清晰：以“项目协作知识流转”为场景，以“主动推送 + 可追溯回答 + 可执行任务闭环”为 Demo 核心。这样既能覆盖赛题要求中的“重新定义知识获取”“构建场景化知识应用”“证明应用效果与价值”，也能充分继承原 PRD 中已经设计成熟的知识入库、检索、引用、报告生成和流式交互能力。

为了更适合挑战赛，本方案将原 PRD 中的 M01-M22 模块重构为办公知识分发场景下的 O01-O32 模块。O 系列模块不仅保留文档解析、树索引、查询改写、树遍历检索、相关性判断、答案生成、LLM 调用管理、流式响应等能力，还新增飞书数据连接器、会议纪要 Action Item 抽取器、群聊争议点识别器、任务状态对账器、分发时机规划器、飞书卡片生成器、用户反馈学习器和效果评估器。系统架构上采用“OpenClaw 主体 + 飞书 CLI 工具层 + Agentic RAG 服务 + 知识原子库 + 推送执行器”的组合，既可以快速做出可运行 Demo，也为后续扩展成企业级产品留出空间。


## 1. 赛题理解与作品定位


飞书 OpenClaw 赛道“企业办公知识整合与分发 Agent”真正考察的不是普通 RAG 的问答准确性，而是参赛者能否把企业协作软件中的信息转化为实际工作流中的知识资产。企业中的知识并不天然存在于某一个文件里，它往往分散在文档正文、会议纪要、群聊上下文、任务评论、邮件、日历邀请、多维表格记录和个人经验中。传统知识库的难点不只是“搜不到”，更是“用户不知道该搜什么”“搜到了也不知道是否过期”“知识没有被推送到需要的人那里”“会议后的任务没有闭环”“同一个问题被反复讨论但没有沉淀”。

本作品建议命名为 **Team Knowledge Pulse Agent**，强调团队知识的“脉冲式感知与推送”。“Pulse”代表系统会周期性、事件式、阈值式地感知团队动态，并把最重要的知识以最合适的形态推送给最需要的人。中文宣传语可采用：**知脉 Agent：让团队知识不再沉睡在文档、会议和群聊里，而是在正确的时刻主动到达正确的人。**

本方案选择“方向 A + 方向 B + 方向 D”的组合型场景。方向 A 可以体现“主动分发”，方向 B 可以体现“场景化知识应用”，方向 D 可以体现“执行闭环和效果证明”。方向 C 的 CLI 终端知识推送可以作为加分项，用于展示 OpenClaw/CLI 的极客体验。在比赛演示中，可以聚焦 B+D，答辩材料中扩展 A+C，既避免 Demo 过散，又能体现方案完整性。


## 2. 与原 PRD 的继承和改造关系


原 PRD 的核心是“面向私有数据资产的智能知识与内容创作 Agent”，用户主要是政企内部的新媒体编辑和内容运营人员，核心场景包括知识问答、稿件撰写、稿件编辑。该 PRD 的技术路线对比赛方案非常有价值，因为它已经解决了企业私有知识管理中的几个关键问题：文档解析、层次化树索引、Agentic RAG、引用溯源、报告生成、SSE 流式交互、MCP 工具封装、模型调用管理、可观测性和权限隔离。

但比赛场景与原 PRD 的差异也很明显。原 PRD 更偏“用户主动发起写作或问答”，比赛更强调“Agent 主动发现知识、主动分发知识、主动推动任务闭环”。因此，本方案不照搬原 PRD，而是做以下改造：

| 原 PRD 能力 | 参赛方案中的继承方式 | 参赛方案中的改造方向 |
|---|---|---|
| 文档入库 M01-M04 | 继续用于飞书 Docs、附件、会议纪要文档的解析和树索引 | 增加飞书消息、任务、评论、日历、邮件等非文档源的结构化处理 |
| Agentic RAG 问答 M05-M12 | 继续用于证据检索、引用标注、无相关内容拒答 | 从“问答”扩展为“推送前知识验证”和“卡片证据生成” |
| 报告生成 M13-M17 | 继续用于周报、会前背景包、复盘报告生成 | 大纲生成改造为“摘要卡片结构规划”和“风险洞察结构规划” |
| 编辑能力 M18-M19 | 可用于人工审核和推送前修改 | 不作为 Demo 主线，作为审核台增强能力 |
| MCP 图像工具 M20 | 可作为附加展示，用于卡片配图或报告封面 | 不是核心能力，避免偏离知识分发赛题 |
| LLM 管理 M21 | 继续作为所有模型调用统一出口 | 增加推送策略、评测打分、隐私脱敏等模型调用类型 |
| 流式响应 M22 | 用于 OpenClaw/飞书卡片生成过程展示 | 增加 Feishu card_push、task_created、bitable_updated 等事件 |

原 PRD 的 PageIndex 思路在本方案中依然是核心。企业办公知识不仅多，而且层级复杂。一个需求文档可能包含背景、目标、接口、验收、讨论记录；一个会议纪要可能包含议题、结论、行动项、风险；一条长群聊可能包含多轮争议和多个事实修正。采用树结构索引，可以把长文和复杂上下文组织成层级摘要，让 Agent 先判断哪个章节、哪个议题、哪个线程值得深入，再读取原文证据。这比简单向量相似度检索更适合解释性强、引用要求高、需要追踪路径的企业场景。


## 3. 场景定义文档


本方案聚焦企业项目团队中的知识流转场景。一个中型项目通常会有产品经理、研发、测试、运营、设计、项目经理和部门负责人参与。团队每天在飞书里产生大量信息：需求文档更新、群聊讨论、会议纪要、任务变更、测试反馈、上线计划、风险同步、日报周报。这些信息看似都有记录，但真正需要用时往往找不到、看不完、分不清版本，也没有自动同步给相关人员。

典型痛点包括：会前准备难，参会人临时打开日历，只知道会议标题，不知道上次会议结论、相关文档、当前任务进度和待讨论风险；会后闭环难，会议纪要里有 Action Items，但需要人工转成任务、补负责人、补截止时间、发群提醒；周报整理难，团队本周做了什么、哪些任务延期、哪些文档修改、哪些风险需要升级，都要人工翻文档和群聊；新人上手难，新人不知道应该读哪些文档、看哪些历史决策、找谁确认问题；知识复用难，同类问题在群里反复问，历史回答散落在消息中，没有沉淀为高密度知识；风险暴露晚，任务延期、需求反复变更、多人争论没有结论，通常要等到项目例会才被发现。

通用搜索解决的是“我知道我要找什么”的问题，但企业办公中的知识需求往往是“我不知道自己应该知道什么”。普通问答虽然可以回答问题，但仍需要用户主动提问；它不会在会议前自动推送背景，不会在会议后自动创建任务，不会在任务延期时主动提醒，也不会把多来源证据整理成可追踪的周报。本方案解决的是“知识到达”的问题，而不仅是“知识检索”的问题。


## 4. 总体产品方案


Team Knowledge Pulse Agent 的产品形态不是单一聊天机器人，而是四种形态的组合：飞书群内智能体、OpenClaw 对话入口、CLI 终端助手和飞书知识沉淀页。飞书群内智能体用于主动推送卡片和接受追问；OpenClaw 对话入口用于配置任务、查看 Agent 思考过程、触发人工审核；CLI 终端助手面向开发者或参赛演示，用命令触发知识查询、报错知识匹配、周报生成；飞书知识沉淀页将确认后的会议结论、周报、FAQ 和项目知识包写回飞书文档或知识库。

系统提供三类主动触发方式。第一类是定时触发，例如每天 9:30 生成今日重点，每周五 17:00 生成团队周报，会议前 30 分钟生成会前背景包。第二类是事件触发，例如会议纪要生成后自动抽取 Action Items，文档更新后自动提醒关联人员，任务状态变化后自动更新推进表。第三类是阈值触发，例如风险分数超过阈值、任务延期超过两天、群聊中某个阻塞问题被反复提及，就自动生成风险预警卡片。

完整业务闭环是：飞书数据源进入系统，经过数据连接与权限过滤，完成文档、会议、消息、任务结构化，生成 PageIndex 树索引和知识原子，构建证据图谱，由场景触发器判断是否需要主动服务，再通过检索与证据校验生成知识产物，经过人工预览确认后推送到飞书卡片、任务、文档或多维表格，最后收集用户反馈并写回长期知识库。


## 5. 知识定义：Knowledge Atom


企业办公场景中的原始数据具有强噪声、高上下文依赖和高时效性。直接把文档 chunk 或群聊消息作为检索结果，容易出现三个问题：第一，信息密度低，用户仍然要读很多上下文；第二，事实边界不清楚，模型容易把讨论过程误当成最终结论；第三，难以判断推送对象和推送时机。知识原子就是为了解决这些问题而设计的中间层。

知识原子不是随便切出来的文本片段，而是“可以被独立消费、可以被证据验证、可以被分发执行”的最小知识单位。每个知识原子至少包含类型、摘要、来源、时间、实体、责任人、置信度、有效期和适用场景。知识原子可以是一个会议决议、一条 Action Item、一个风险点、一项指标变化、一段背景事实、一个争议结论、一条版本变更、一条阻塞原因。每个知识原子都必须绑定来源、时间、责任人、置信度、适用场景和分发对象。这样系统才知道“什么知识值得推送、推给谁、什么时候推、以什么形式推”。

| 类型 | 定义 | 示例 | 主要来源 |
|---|---|---|---|
| Fact | 客观事实或数据 | “接口 v2 将于 5 月 10 日上线” | 文档、会议、任务 |
| Decision | 已确认决策 | “本期先保留旧字段，下一期再下线” | 会议纪要、群聊结论 |
| ActionItem | 待办事项 | “张三周三前补充压测报告” | 会议纪要、群聊、任务 |
| Risk | 风险点 | “测试环境不稳定可能影响联调进度” | 群聊、任务评论、纪要 |
| Blocker | 阻塞原因 | “缺少第三方接口权限” | 任务评论、群聊 |
| Change | 版本变更 | “需求文档新增权限校验章节” | 文档更新记录 |
| Question | 未解决问题 | “是否支持海外租户仍需确认” | 群聊、会议 |
| Insight | 综合洞察 | “本周延期主要集中在接口联调和数据准备” | 多源汇总 |
| FAQ | 可复用问答 | “如何申请测试环境账号” | 历史消息、文档 |
| Reminder | 提醒类知识 | “明天评审前需确认 API 字段” | 日历、任务 |


## 6. 系统总体架构


系统采用六层架构：飞书数据源层、工具连接层、数据处理层、知识索引层、Agent 编排层和交互分发层。飞书数据源层包括 Docs、Minutes、消息、任务、日历、邮箱、多维表格、云空间附件。工具连接层包括 OpenClaw 飞书插件、飞书 CLI、MCP Server、自定义 API Wrapper。数据处理层负责解析、清洗、去重、线程聚合、任务快照、权限过滤。知识索引层包括 PageIndex 树索引、知识原子库、证据图谱、向量索引、元信息表。Agent 编排层包括 LangGraph/OpenClaw 工作流、场景触发器、检索器、生成器、审核器、分发器。交互分发层包括飞书卡片、飞书任务、飞书文档、多维表格、OpenClaw 对话、CLI 提示。

建议服务划分为 Knowledge Ingestion Service、Agent Intelligence Service、Feishu Connector Service、Distribution Service、Evaluation Service 和 Demo Dashboard。Knowledge Ingestion Service 继承原 PRD 服务 A，但从文档扩展到办公多源；Agent Intelligence Service 继承原 PRD 服务 B，增加主动触发和分发；Feishu Connector Service 封装飞书 CLI/API 调用；Distribution Service 负责卡片、任务、文档、表格写入；Evaluation Service 用于生成比赛效果验证报告；Demo Dashboard 用于展示链路和日志。


## 7. 可运行 Demo 设计


Demo 应证明三件事：第一，Agent 能读取飞书生态中的多源上下文，而不是只能处理用户手动粘贴的文本；第二，Agent 能主动触发服务，而不是只能被动问答；第三，Agent 输出的知识产物准确、可引用、可执行，并且能提升效率。

建议准备一个模拟项目“Alpha 智能报表平台”。该项目包含 3 篇飞书文档：项目 PRD、接口设计文档、上线计划；2 份会议纪要：需求评审纪要、接口联调纪要；1 个飞书群聊：包含 30-50 条与需求变更、测试阻塞、接口字段有关的消息；8 条飞书任务：其中 3 条完成、3 条进行中、2 条延期；1 个日历会议：标题为“Alpha 项目周会”；1 个多维表格：重点事项推进表。这些数据应提前准备好，并保证其中存在可被 Agent 发现的事实：例如某个接口字段本周变更、某个任务延期、某个会议决议尚未落实、某个风险在群聊中重复出现。

Demo 流程一是会前背景卡片。展示飞书日历中即将开始的“Alpha 项目周会”，触发 Agent 自动读取会议元数据、参会人、上次会议纪要、项目 PRD、未完成任务和最近群聊，生成卡片并推送到会议群。Demo 流程二是会后 Action Items 转任务。展示会议纪要，Agent 抽取待办、匹配负责人和截止时间、生成任务创建预览，确认后创建飞书任务并更新多维表格。Demo 流程三是每周风险洞察。Agent 汇总本周文档变更、任务状态、会议纪要和群聊，生成周报卡片和飞书文档，同时展示评测指标。


## 8. 效果验证报告设计


效果验证需要回答三个问题：准确性、效率和接受度。准确性是系统生成的知识卡片是否真实、可引用、少幻觉；效率是相比人工搜索和人工整理，系统是否节省时间；接受度是用户是否愿意点击、确认、使用这些知识产物。

建议设置三组对照。Baseline A 是人工搜索飞书文档和群聊，记录完成同一任务所需时间。Baseline B 是普通 LLM 摘要，直接粘贴纪要，检查信息遗漏和无引用问题。Proposed 是 Team Knowledge Pulse Agent，使用多源检索、证据校验、主动卡片。

| 指标 | 定义 | 目标值 |
|---|---|---|
| Citation Accuracy | 生成结论的引用是否真实支持该结论 | >= 90% |
| Evidence Coverage | 关键结论是否覆盖主要来源 | >= 85% |
| Hallucination Rate | 无来源或来源不支持的事实占比 | <= 5% |
| Knowledge Compression Ratio | 原始文本字数 / 卡片字数 | >= 8x |
| Action Item Recall | 会议待办抽取召回率 | >= 85% |
| Action Item Precision | 抽取待办准确率 | >= 85% |
| Time Saving | 相比人工整理节省时间 | >= 50% |
| Card Click Rate | 用户点击详情或证据链接比例 | >= 30% |
| Task Confirmation Rate | 自动任务被用户确认比例 | >= 70% |
| User Rating | 用户对卡片有用性的 1-5 分评分 | >= 4.0 |


## 9. 安全、权限与幻觉控制


企业办公 Agent 的最大风险是权限和数据泄露。系统必须做到不跨租户检索、不跨用户授权范围检索、不把私聊内容推送到群聊、不把高密级文档摘要推送到低权限群、写操作必须先预览再确认、所有输出保留 trace 方便审计。

本方案从五层控制幻觉：检索层通过 O15 过滤不相关证据；Prompt 层要求每条事实绑定 evidence_id；生成层在没有证据时输出“不确定”或“待确认”；后验校验通过引用支持判断模型检查结论是否被证据支持；人工确认层对涉及任务创建和群发的内容由用户确认。

当不同来源冲突时，不能强行合并成一个结论。系统应输出“存在信息冲突”，列出不同来源的不同说法，并建议在会议中确认。敏感信息包括客户名称、合同金额、个人隐私、密级文档、未公开战略、邮箱私信等。系统需要在入库时记录 security_level，生成前根据目标群权限过滤证据，输出前进行 PII 和密级扫描，对敏感实体进行脱敏或仅私聊发送。


## 10. 开发计划与 Codex 分阶段任务单


阶段 P0 是最小闭环 Demo，目标是打通“读取飞书数据 -> 检索证据 -> 生成卡片 -> 推送/预览”的最小链路。任务包括初始化 FastAPI 项目结构、封装飞书 CLI 的文档读取和会议纪要读取、定义数据模型、实现本地 JSON 缓存、实现手动触发接口、实现会前背景卡片、实现 dry_run 卡片预览、实现基础 trace 日志、编写测试样例和录制第一版 Demo 视频。

阶段 P1 是会后 Action Items 闭环，目标是完成“会议纪要 -> 待办抽取 -> 任务创建预览 -> 飞书任务写入”。任务包括实现会议纪要解析器、Action Item 抽取 Prompt、负责人和截止时间推断、重复任务检测、任务创建 dry_run、人工确认后创建任务、会后总结卡片、多维表格更新和任务字段完整性评测。

阶段 P2 是周报洞察与风险预警，目标是完成周期性知识总结和风险阈值触发能力。任务包括实现时间窗口聚合、同步本周文档变更、任务状态、会议纪要和群聊、实现知识原子抽取和分类、风险分数计算、周报洞察生成器、风险预警卡片、反馈按钮和反馈记录、评测指标面板、Baseline 对照数据和效果验证报告。

阶段 P3 是答辩优化与工程加固，目标是提升稳定性、可解释性和演示体验。任务包括增加 Demo Dashboard、卡片样式美化、OpenClaw 对话入口命令、CLI 命令 `tkp weekly-insight`、异常处理和缓存兜底、答辩 PPT 和演示脚本、失败案例分析、安全合规说明、GitHub README 和最终提交包。

### O01：飞书数据连接器（Feishu Data Connector）

**模块定位：** 通过飞书 CLI 或 OpenClaw 飞书插件读取 Docs、Minutes、群聊消息、任务、日历、邮件、多维表格等数据源。该模块必须处理授权、分页、增量同步和失败重试。

**输入：**

- 当前租户和用户上下文，包括 tenant_id、user_id、授权范围、项目空间 ID。
- 上游模块传来的源对象、触发上下文或检索任务。
- 系统配置，例如最大读取条数、时间窗口、是否启用人工确认、是否允许写入飞书。
- 如果来自 OpenClaw 对话入口，还需要包含对话 session、最近用户指令和执行模式。
- 如果来自定时或事件触发，还需要包含 trigger_id、trigger_type、event_payload 和触发时间。

**核心处理逻辑：**

1. 首先进行输入合法性校验，确保字段完整、权限范围清晰、时间窗口明确。
2. 根据模块职责调用对应工具或模型能力，执行 docs.read, minutes.search, message.search, calendar.search, task.list, bitable.read 等子任务。
3. 对输出结果进行结构化封装，保证下游模块不依赖上游数据源的原始格式。
4. 如果处理失败，写入 agent_trace 和 llm_call_log；若属于可恢复错误，则交给 O30 异常与降级处理器。
5. 对涉及用户数据或企业敏感信息的字段，调用 O29 安全脱敏器进行预处理或出站检查。
6. 对模块生成的结论保留 evidence_id、source_id、source_type、updated_at 和 path，方便后续卡片引用与效果评估。
7. 对可能影响用户的操作，输出 preview_mode 字段，交由 O24 人工审核与确认器处理。

**输出：** `raw_feishu_event / raw_feishu_object`。

**验收标准：**

- 模块能够在 Demo 数据集上稳定执行，失败时返回明确错误码。
- 输出 JSON 字段稳定，能被下游模块直接消费。
- 关键结果必须有日志记录，包括输入摘要、输出摘要、耗时、调用工具、异常信息。
- 如果模块产生面向用户的结论，必须保留来源证据 ID，不能只保存生成文本。
- 如果模块涉及写操作，必须支持预览模式和确认模式，避免比赛演示中出现不可逆误操作。
- 模块应至少包含 3 类测试：正常路径、空结果路径、异常/权限失败路径。
- 模块应在 README 中写清楚如何独立运行和如何接入主图。

**与原 PRD 的关系：**

该模块参考原 PRD 中“模块可独立开发、独立测试、上下游通过标准对象传递”的设计方式。与原 PRD 不同的是，本方案将模块输出从“回答/报告”扩展为“知识原子、证据图谱、分发计划、卡片、任务、效果指标”等办公协作产物。

```python
    structured_sources: list[dict]
    retrieval_jobs: list[dict]
    evidence_chunks: list[dict]
    verified_evidence: list[dict]
    knowledge_atoms: list[dict]
    distribution_plan: dict | None
    draft_outputs: list[dict]
    review_status: str
    final_actions: list[dict]
    metrics: dict
    trace_id: str
```

这个状态对象贯穿整个图执行过程，既能支持 OpenClaw 的多轮对话，也能支持定时和事件触发。比赛答辩时可以把 trace_id 对应的执行链路展示出来，说明 Agent 不是黑盒生成，而是经过触发、检索、校验、压缩、审核、分发等多个步骤。

### 12.2 会前背景包工作流

```text
Calendar Event Trigger
  -> Load meeting metadata
  -> Identify participants and project
  -> Retrieve related docs/minutes/tasks/messages
  -> Verify evidence
  -> Generate pre-meeting brief
  -> Create Feishu card
  -> Human preview optional
  -> Push to meeting group
```

会前背景包卡片建议包含会议主题和时间、上次相关会议的关键结论、当前未完成事项、近期文档变更、需要本次会议确认的问题、相关来源链接和一键追问按钮。这个工作流最容易体现“主动分发”的价值，因为用户还没有提问，系统就已经根据日历事件和项目上下文把知识送到了参会人面前。

### 12.3 会后行动项工作流

```text
Minutes Created Event
  -> Load minutes transcript
  -> Extract decisions and action items
  -> Match owner and deadline
  -> Check conflict with existing tasks
  -> Generate task creation preview
  -> Human confirm
  -> Create Feishu tasks
  -> Push post-meeting summary card
  -> Update key item bitable
```

会后行动项工作流最能体现“知识转行动”。系统不是简单总结会议，而是把会议中的 Action Items 转化为飞书任务，并把来源证据绑定到任务描述里。对于缺少负责人或截止时间的事项，系统应标记为 need_confirm，而不是强行猜测。

### 12.4 每周洞察工作流

```text
Weekly Schedule Trigger
  -> Load week window
  -> Aggregate docs changes, tasks, messages, minutes
  -> Extract knowledge atoms
  -> Build progress/risk matrix
  -> Generate weekly insight card and doc
  -> Push to department group
  -> Write back to weekly report doc
  -> Calculate metrics
```

每周洞察卡片建议包含本周完成事项、本周关键决策、延期和阻塞事项、下周重点、需要管理者关注的风险、数据来源覆盖范围和反馈按钮。该链路最适合做效果验证，因为可以比较人工写周报和 Agent 生成周报的时间差、遗漏率和引用准确率。

### 12.5 阈值风险预警工作流

风险预警可以作为加分项。系统持续监控任务延期、群聊负面关键词、文档反复修改、会议中未解决问题数量等信号。当风险分数超过阈值时，主动推送风险卡片。

```text
risk_score = 0.35 * delay_days_score
           + 0.25 * blocker_message_score
           + 0.20 * unresolved_question_score
           + 0.10 * doc_change_frequency_score
           + 0.10 * meeting_repeat_score
```

其中每项分数都应有可解释来源。比如 delay_days_score 来自任务截止日期，blocker_message_score 来自群聊中“卡住”“阻塞”“权限不够”等关键词及语义判断，meeting_repeat_score 来自相同议题多次出现在会议纪要中。


## 13. 飞书 CLI / OpenClaw 工具设计

### 13.1 工具封装原则

比赛 Demo 中不建议把所有飞书 API 从零封装一遍。更可行的方式是：使用飞书 CLI 或 OpenClaw 飞书插件提供的能力作为底层工具，在 Agent 内部封装为更语义化的 Tool。比如底层可能是读取文档命令，上层封装为 `read_project_doc(project_id, doc_keyword)`；底层可能是任务 API，上层封装为 `create_action_item_task(action_item)`。

工具封装要遵循以下原则：

- 工具输入必须结构化，避免把长自然语言直接传给工具。
- 工具输出必须带 source_id、url、title、updated_at 等元信息。
- 写操作必须支持 dry_run。
- 权限不足时要返回可解释错误，而不是直接失败。
- 所有工具调用都写入 trace，便于答辩演示。
- 读取结果应统一转成 SourceObject，避免后续模块感知底层飞书接口差异。
- 工具调用应支持超时和重试，Demo 现场应允许切换到本地缓存数据。

## 18. 评测用例库

为了让效果验证更有说服力，本方案设计一组覆盖会前、会后、周报、任务对账、风险预警、知识问答的评测用例。每个用例包含输入来源、期望输出、关键证据和评价重点。下面列出的用例可直接转化为 `evaluation_case.jsonl`。


### Case 001：会后行动项 - Beta 客户数据中台

**输入来源：** `接口设计文档`、`任务评论`、相关任务记录、近 7 天群聊消息。

**场景描述：** 团队正在推进 `Beta 客户数据中台`，最近协作中出现了“测试环境权限不足”的问题。用户希望 Agent 不只是回答某个单点问题，而是主动识别当前场景下需要同步给团队的高密度知识。

**触发方式：** 事件触发。

**期望输出：**

1. 生成一张结构化飞书卡片，标题中明确项目和场景。
2. 提炼 3-5 条关键事实或结论，每条都必须带来源证据。
3. 如果存在待办，输出负责人、截止时间、优先级和来源。
4. 如果存在风险，解释风险原因、影响范围和建议处理动作。
